# 里程碑与验收

> 状态：所有条目均为计划，尚无实现或实验验收证据。来源为[完整技术设计](technical-design.md)第 14、17 节；交付物细分为执行建议。

## 推进原则

先证明局部矩阵可读且被使用，再训练条件生成；条件生成稳定后才加入纠错和策略。S1 用于尽早验证机制，S2 用于首个完整系统，S3 用于研究级消融。S4/S5 需以小规模预算匹配收益为启动依据。

所有验收都需链接实际代码提交、配置、数据版本、实验记录和原始结果。缺少结果的条目保持“待验证”，不能因文档、接口或脚本存在就标记模型能力完成。

## 每个里程碑的验收记录

- [ ] 明确要检验的假设和唯一主要问题。
- [ ] 提前固定数据、指标、质量门槛和成本上限；定量阈值由预实验和研究预算确定，目前尚未定值。
- [ ] 保存可复现配置、种子、代码提交、checkpoint 和评测产物。
- [ ] 与对应基线在相同数据和预算口径下比较，说明未匹配的部分。
- [ ] 报告负向结果、强制预算终止和失败分层。
- [ ] 基于证据标记通过／未通过／证据不足，并记录下一步。

## 最小可行研究结论

以下五项需同时得到支持，才可初步认为联合机制有独立研究价值：

1. 同样本和推理计算约束下，允许 EDIT 的动态状态模型优于匹配的无 EDIT 基线。
2. 固定同一潜在矩阵时，回答详略可控且核心事实与结论一致。
3. Decoder 确实读取 64 槽窗口，矩阵与窗口干预具有可解释的效果。
4. 增加块数与修订轮数的收益可在跨任务、多随机种子条件下重复。
5. 报告延迟、FLOPs、显存、操作行为及失败案例。

这些是研究判断条件，不能当作已经实现的效果或对未来实验的保证。各项证据按[实验规范](experiments.md)记录。
